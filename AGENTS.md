# AGENTS.md — Cheat-sheet operativo para agentes

Sistema CRM inmobiliario **en producción real** (bienenhaus.com.ar) con datos de clientes. El `README.md` documenta arquitectura, módulos, DB y flujos en profundidad — leerlo antes de cambios grandes. Este archivo es solo lo que ya causó bugs o no se puede inferir de los archivos.

## Reglas duras

- **Producción con datos reales**: nunca DELETE/TRUNCATE/DROP ni migraciones destructivas sin backup y aprobación explícita. No hay staging.
- **⚠️ PowerShell corrompe UTF-8 — regla dura de encoding**: NUNCA usar `Get-Content`/`Set-Content`/`Out-File` de PowerShell 5.1 para leer o escribir archivos con acentos/emoji (HTML, JS, CSS, MD, SQL). PS 5.1 lee UTF-8 como CP1252 y al re-escribir hornea doble-encoding (mojibake "DÃ³lares") — incidente real 2026-10-12: dos resoluciones de conflicto de rebase con Get-Content+Set-Content corrompieron TODO admin.html (342 textos) y llegó a producción. Para leer: usar el tool Read. Para escribir/transformar archivos: `node` con `fs.readFileSync(path,'utf8')`/`writeFileSync(path, data,'utf8')` (ver `scripts/recover-admin-html.mjs`). Para resolver conflictos de rebase con contenido no-ASCII: node script, jamás PowerShell.
- **Directiva del dueño: no usar subagentes** — trabajar directo con herramientas.
- Todo comando git lleva prefijo `$env:GIT_MASTER='1';` (PowerShell, hook del equipo): `$env:GIT_MASTER='1'; git status`.
- Commits en español, minúsculas, formato `modulo: mensaje` (ej: `perf: hero cloudinary, fotos comprimidas`). Antes de push: `git pull --rebase`; si rechaza, rebase — jamás force.
- NO stagear untracked ajenos al trabajo: `gvamax-export/`, `HOJA DE VISITA.pdf`, `meta.txt`, `scripts/scan-refs.ps1`.

## Flujo de cambios (no hay build step)

1. Editar JS/CSS/HTML.
2. `npm run bump` — sube los `?v=N` de los assets con cambios (git diff vs HEAD) en todos los HTML del root. Sin esto, producción sirve una mezcla de versiones vieja/nueva → bugs fantasma. Commitear los HTML junto con los assets.
3. `node --check assets/js/<cada-js-editado>.js` — es el único "typecheck" que existe.
4. `npm test` — Playwright en modo lectura contra producción; los de admin requieren `BH_TEST_ADMIN_EMAIL`/`BH_TEST_ADMIN_PASSWORD`.
5. Commit + push a `main` → Cloudflare Pages deploya solo (build vacío, output `/`).
6. Local: `python -m http.server 8791`.

## Cliente autenticado del admin — `getAuthedClient()` es SINGLETON (2026-10-30)

- **Síntoma**: warning en consola durante la subida de contenido a YouTube → `GoTrueClient@bh-authed-client:1 Multiple GoTrueClient instances detected in the same browser context`. No es un error, pero Supabase avisa que puede dar comportamiento indefinido al concurrir bajo el mismo storage key.
- **Causa raíz**: `getAuthedClient()` (admin-app.js) chequeaba la caché **ANTES** del `await` de `getSession()` → varias llamadas concurrentes (el Studio de Contenido dispara varias en paralelo: historial, cola, categorías, auditoría) pasaban el chequeo con el cliente en `null` y **creaban un GoTrueClient cada una** con el storageKey `bh-authed-client`.
- **Regla dura**: el cliente autenticado se crea **UNA sola vez** (guard por promesa para las llamadas concurrentes). Cuando Supabase rota el token, **NO se recrea**: se actualiza la cabecera `Authorization` (`client.headers.Authorization` + `client.rest.headers`, porque PostgrestClient **copia** las cabeceras al construirse y vuelve a copiarlas en cada `.from()`/`.rpc()`). FunctionsClient/StorageClient leen `client.headers` en vivo.
- **StorageKey propio**: `bh-authed-client` (NO el default) — si se usa el default, el cliente autenticado sería la instancia 1 del mismo key que `window.supabaseClient` → warning igual.
- **No destruir el cliente en SIGNED_OUT**: se limpian token y cabeceras, pero el cliente se conserva (recrearlo en el próximo login dispara el warning de nuevo).
- **JWT base64url**: los JWT usan `base64URL` (`-`/`_`), que `atob()` estándar rechaza → `exp` ilegible → el caché de expiración nunca funciona. `parseJwtExpiry()` normaliza a base64 antes de decodificar.
- El bloque está delimitado con markers `BH-AUTH-CLIENT:START/END` porque `tests/admin-auth-client.spec.js` lo evalúa en un sandbox (reproduce el contador de instancias de @supabase/auth-js): 5 llamadas concurrentes deben crear **1** cliente y **0** warnings.

## ⚠️ Código vs schema real (auditoría 2026-10-20: 13 bugs de la MISMA raíz)

La clase de bug más cara del proyecto: **código escrito contra columnas/tablas imaginarias**. Como casi todos los flows tragan errores con `.catch(() => ...)` o ignoran `result.error`, fallan en silencio total (features que "existen" pero jamás funcionaron). Hallazgos reales ya corregidos:

- `lead_offers` NO tenía `status`/`counterparty`/`updated_at` — el deal room guardaba aceptar/rechazar en `offer_type`, **destruyendo el tipo real**. Ahora el estado va en `lead_offers.status` (`pending|accepted|rejected`) y `offer_type` es SOLO el tipo (cliente/counter). Migración `20261020000001`.
- `audit_log` usa `user_id` — `actor_id` no existe (ml-disconnect/ml-publish insertaban audit muerto). Y **`activity_log` NO existe** — la tabla es `audit_log` (ml-oauth insertaba a una tabla fantasma); requiere `action` + `module` NOT NULL.
- `properties`: la fuente de verdad del precio es **`price_usd` + `price_currency`** (el trigger `sync_property_price_fields` pisa `price`/`currency` desde ellas en cada INSERT/UPDATE; `price_ars` es columna GENERADA — enviarla da error). `property_code` lo genera el trigger `set_property_code_on_insert` (prefijo `ML-` si `source_type='ml'`). **NO existen**: `code`, `slug`, `location_id`, `amenities`, `expenses`, `floors`, `operation_type`, `favorites_count`, `views_count` — el import de ML (`ml-import-listings`/`ml-sync-import`) estaba 100% roto por esto hasta 2026-10-20.
- `property_ml_meta` solo tiene: `property_id, ml_item_id, status, price, permalink, last_sync_at, last_sync_status, created_at, updated_at` — `category_id`/`listing_type_id`/`raw` no existen.
- `owner_tasks` usa **`assigned_to`** (FK agents) y **NO tiene `title`** (el título va en `description`); `lead_tasks` SÍ tiene `title` y usa `due_at` mientras `owner_tasks` usa `due_date`.
- `lead_activities` usa `created_by` — `user_id` no existe (el timeline del lead pasó meses mostrándose vacío por esto).
- `leads`: contactos son `full_name`/`phone`/`email` — `contact_name`/`contact_phone`/`contact_email`/`tags`/`score`/`broker_id` NO existen (agente = `assigned_to`). Al mostrar un objeto en un panel, **verificar que el SELECT traiga todos los campos que el render lee** — el bug corruptor de `preferred_contact_method` era exactamente esto (el select del panel no lo traía, el dropdown caía al fallback WhatsApp y al guardar PISABA el valor real; `computePropertyMatches` quedó medio ciego por lo mismo con `preferred_type`/`preferred_rooms`/`budget_usd`).

**⚠️ Fields/labels de ENUM: `leads.stage` es el enum `lead_stage` (hallazgo 2026-11-08, la clase que más costó de todas)**: un filtro PostgREST `.not('stage','in','(...)')` con labels que NO existen explota en runtime con `22P02 invalid input value for enum` y la llamada devuelve `data:null` con el error ignorado — la consolidación de leads de ML (`findConsolidableMlLead` en ml-webhook) estuvo **rota desde su nacimiento (13/10 → 8/11)** por incluir `cerrado_vendido`/`vendido`/`descartado` (labels que jamás existieron): cada contacto de la misma persona creado de nuevo en vez de mergear; nadie lo vio. Labels reales (verificados con `enum_range(lead_stage)`): `nuevo, contactado, calificado, visita_agendada, visita_realizada, negociacion, cerrado_ganado, cerrado_perdido` — terminales = solo los 2 últimos. NUNCA agregar labels "por las dudas" a una lista de exclusion de enum. Fix aplicado en ml-webhook + rela-callbacks (constante + `if (error)` antes del `return data ?? null`); guard: `tests/stage-enum-contract.spec.js` (falla si vuelta a labels inventados o si el `error` de la query no se lee).

**Cómo detectar antes de deployar**: comparar columnas de `.from('x').select/insert/update` contra `information_schema.columns` (script de un solo query + regex; los falsos positivos son embeds `tabla(col, ...)` y keys de JSONB). Si la tabla tiene enums (`lead_stage`), comparar TAMBIÉN los labels usados en filtros contra `enum_range(...)` — las columnas todas existen ≠ los labels del filtro existen. Los catch silenciosos son el amplificador: si un flow nuevo "no hace nada", asumir schema mismatch y mirar el `result.error` real.

- Las notificaciones de tópicos de ML **no vienen firmadas** (no hay header documentado): la barrera real del webhook es el binding (`application_id` + `user_id` de `ml_connection`) + el re-fetch del recurso con el token del vendedor. `ML_WEBHOOK_SECRET` se pasa como `auth_token` al registrar los tópicos y solo verificaría un hipotético `x-meli-signature` con HMAC del body — nunca contra el secreto en plano (bug real 2026-10-07: mataba toda notificación).

Callback URL: `${SUPABASE_URL}/functions/v1/ml-webhook`; tópicos para inmuebles: **VIS Leads** (subtópicos Question/WhatsApp/Call/Visit request/etc.). Los tópicos questions/items NO traen consultas de inmuebles. Si "las consultas de ML no llegan al CRM": verificar eso primero; el panel (Portales → ML) muestra la guía cuando el endpoint da 'gone'.

El texto de una pregunta se pide aparte con `external_id` → `/questions/{id}`. Hoy ambos flujos hacen INSERT al ledger `ml_questions` como claim (UNIQUE `question_id`); quien pierde (23505) NO actúa por su cuenta — si tiene identidad, consolida en el lead del ganador. Además la vía `questions` **nunca crea leads** (en inmuebles ML anonimiza identidad — el dueño no quiere filas vacías en el CRM): claima el ledger, responde con la plantilla y nada más. Los leads se crean solo desde `vis_leads` CON identidad (nombre o email/teléfono/whatsapp), y si la misma persona toca otra publicación el evento se mergea al lead existente con `mergeMlEventIntoLead` (rellena campos vacíos. vincula la propiedad extra en `lead_properties`, deja traza "Evento ML vinculado: <id>" para que las notificaciones de estado de ese contacto también casen) — nunca sobre etapas terminales (⚠️ la consolidación estuvo ROTA del 13/10 al 8/11/2026: la exclusión de stages usaba labels inventados del enum → 22P02 → data null en silencio y TODAVÍA cada consulta creaba lead — fix y detalle en la sección Código vs schema real). Señal: eventos `failed` con "HTTP 403" en ml_webhook_events (las notificaciones quedan registradas y se re-importan cuando se habilite — no se pierden).

Fix: `toMlPlainText()` en `_shared/ml.ts` aplicado en TODOS los envíos (ml-sync `mlSetDescriptionValidated`, ml-publish `setDescription`, shared `mlSetDescription`). NO poner emojis en descripciones si el texto se manda a ML — el sanitizador los remueve solo para ML; CRM/ficha/landing conservan el original.
- **Cola `ml_sync_queue` con dedup (incidente 2026-10-21)**: el eco sync→ML→webhook(items)→enqueue creaba un job por notificación SIN deduplicar — 42.676 jobs para UNA propiedad ahogaron la cola (procesa 120/hora) y los updates nunca llegaban. `ml_enqueue`/`ml_enqueue_batch` ahora ignoran el insert si ya hay un job `pending`/`processing` para la misma propiedad+operación (los jobs no llevan payload: el update procesa con data fresca de la DB, así que 1 job ≡ 42.000). Si la cola vuelve a inflarse: mirar `count(*) WHERE status='pending'` — sano es <20.
- **`ml_listings.ml_status` es lo que lee el módulo Propiedades — el sync debe refrescarla (bug 2026-10-24)**: DOS tablas trackean el estado ML y divergían. `property_ml_meta.status` la refresca ml-sync en cada update exitoso; `ml_listings.ml_status` solo la escribían ml-publish (al publicar, con el `not_yet_active` que ML devuelve en creación — normal, el item tarda minutos en activarse) y ml-publish remove. Resultado: TODA publicación nueva quedaba "Pendiente ML" para siempre aunque estuviera live (10 afectadas; 3 con eco vivo y ML devolviendo `active` en cada sync, 7 zombie cuyos jobs murieron en la era del sync roto y ML no re-notifica items sin cambios → backfill manual con `ml_enqueue(property_id,'update',ml_item_id)` desde SQL). Fixes: ml-sync ahora TAMBIÉN actualiza ml_listings (ml_status+last_sync) en cada éxito; ml-publish remove también fija `meta.status` (quedaba 'active' tras cerrar, caso DA-P0001); webhook handleItems reintentó el enqueue (x1, 1.5s) para que un 502 transitorio de PostgREST no prenda el badge Portales "N err" 24h + fallback a ml_listings cuando no hay meta. Verificación de estado real de un item SIN depender de la DB: página pública `articulo.mercadolibre.com.ar/MLA-{id}` (cuidado: ML bot-wallea batches, de a uno con retries).
- **Items CERRADOS en ML rechazan updates con 400 engañosos, y el estado guardado puede ser mentira de meses (caso DA-P0008/MLA2130706103, 2026-10-24)**: ML responde al PUT sobre item cerrado con `field_not_updatable` (240) / `item.price.not_modifiable` (339) — igualito a un item en pre-activación, NO distingue. El estado `not_yet_active` guardado al crear (27/9) era mentira: el GET reveló que el item estaba `closed` (cerrado directo en panel de ML en algún momento). ml-sync ahora: (1) ante 400 parsea los `references` y reintenta sin los campos bloqueados, (2) ante fallo del update hace un GET best-effort y deja registrado el estado REAL en ml_listings + meta (el job igual falla y queda visible). Sin (2), el badge seguiría mintiendo para siempre. Clase de bug: **el estado guardado a la altura de la creación/update vale solo hasta el siguiente evento de ML — sin verificación continua es una conjetura**.
- **Quitar un item sin activar: DELETE → 405, no 'closed' mentiroso (fix 2026-11-01)**: `closeMlItem` para items `not_yet_active` hacía PUT closed → DELETE → 405 method_not_allowed → re-throw → **500 con el JSON crudo de ML** (y el estado en DB quedaba `closed` aunque el item seguía vivo). Ahora ante fallo del DELETE (no 404) `fetchItemStatus` hace un GET best-effort del estado REAL y `closeMlItem` lanza el error codificado `close_blocked_unactivated:<estado>:<mensaje>` — el remove path lo detecta, escribe ese estado en `ml_listings` + `property_ml_meta` (`last_sync_status:'error'`), audita `publish_close_blocked` y responde **409** `{code:'ML_ITEM_NOT_ACTIVATED'}` accionable (el 404 conserva el clean-close). En el mismo lote: los errores de ML llegan al panel solo con causas **fatales** (`summarizeMlError` filtra type error/invalid — antes 300+ chars de warnings ahogaban el dato real en el toast de ~260), y `upsertListing` del update path escribe la **meta completa** (status/permalink/price/last_sync) — antes dependía del eco ml-sync/webhook que puede no llegar jamás (los 7 zombies DA-P0008). Guards estáticos: `tests/ml-publication-fixes.spec.js`.

## Supabase (proyecto único = producción)

- Proyecto `rnldqiwwzhjnurkguihu`. Migraciones vía MCP `supabase_apply_migration` (quedan en `supabase/migrations/`).
- RLS en las **72 tablas** (100 % de cobertura, re-verificado 2026-11-11 contra producción). Las tablas con RLS ON pero **sin policies** (club "solo service_role", el advisor las lista como INFO intencional): `ml_oauth_states`, `ml_sync_queue_failed_archive` (sin PK, es tabla de archivo), `rela_tokens`, `zernio_webhook_events`. `zernio_config`/`property_sequences`/`ml_webhook_events` YA TIENEN policies (no revocar por error: `zernio_config` tiene 3 policies gated a `key='api_key'` + `role='super_admin'` — el `sync_secret` queda inaccesible para authenticated; `property_sequences` service_role_all; `ml_webhook_events` SELECT para authenticated).
- Funciones `SECURITY DEFINER` de acceso público por token (`portal_get_portal_data`, `portal_validate_token`, `get_visit_by_token`, `update_visit_status_by_token`, `log_visit_public_action`, y `get_sidebar_badge_counts` para authenticated) **conservan** EXECUTE — no revocar.
- **No revocar EXECUTE a `authenticated` en funciones usadas por cadenas de trigger/DEFAULT** (ej: `generate_property_code`, `set_property_code`, triggers de visits/leads). Incidente real 2026-09-28: una revoca masiva rompió el alta de propiedades ("permission denied for function generate_property_code") y hubo que revertirla. Hardening vigente y seguro: REVOKE a `PUBLIC` en las 10 funciones internas de CRM + GRANT explícito a `service_role` + `search_path` fijado.
- Tras cualquier migración de permisos: verificar con `has_function_privilege` **la lista completa** de funciones tocadas × (anon, authenticated, service_role) — no un subconjunto.
- **⚠️ Toda función NUEVA hereda `EXECUTE TO PUBLIC` por defecto (hallazgo 2026-11-11, migración `20261111000002`)**: el hardening del 2026-10-15 arregló las funciones EXISTENTES pero no tiene red de redes — `log_property_price_change` (16/10) y `revoke_owner_tokens_on_deactivate` (30/10) nacieron después y volvieron al advisor (17 vs baseline 15). Regla por cada `CREATE ... FUNCTION` nueva en una migración: (1) `SET search_path = ''` en el DDL, (2) REVOCAR `PUBLIC`+`anon` y GRANT explícito según invocador real (mirar si su tabla tiene policies anon), (3) en el MISMO commit, re-escanear el advisor de seguridad (security + performance) y comparar contra el baseline: **anon-SECDEF 15** (13 RPC por token + `compute_lead_score`/`notify_new_lead` justificadas), **search_path_mutable 0**, `rls_enabled_no_policy` = el club de 4 arriba.
